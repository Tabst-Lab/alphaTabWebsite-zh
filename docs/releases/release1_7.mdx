## 1.7.0

自 1.6.0 发布以来已过去半年，alphaTab 再次带来了包含新功能的版本。
我一直希望加快发布周期，但这总是取决于我能投入多少时间进行开发。
毕竟，alphaTab 仍然主要是一个个人项目 😁

本次发布聚焦于两个主要领域，带来了一系列新功能。

本次发布的一个特别之处在于，我今年大部分改动都是在旅途中完成的。这就是为什么某些功能的开发时间可能比在家专注开发时要长一些。正如你所料，当你在苏格兰、威尔士和日本等美丽国家旅行时，进度自然会慢一些。😆

### 音乐记谱

#### 渲染：改进 SmuFL 规范兼容性
https://github.com/CoderLine/alphaTab/pull/2257

> SMuFL 是一种规范，提供了一种标准方式，将传统音乐记谱所需的数千个音乐符号映射到 Unicode 基本多文种平面中的专用区，用于单个（与格式无关的）字体。
> https://www.smufl.org/

多年来，alphaTab 一直使用 SmuFL 字体 Bravura 来渲染音乐记谱符号。但从历史上看，很多视觉方面的东西，如间距、填充和其他排列，都是源自 alphaTab 早期的自定义开发。
虽然乐谱看起来通常不错，但 SmuFL 规范的各个方面并未被遵循，导致按照该规范显示"不正确"。

通过这些改动，我们清理了多年来在音乐记谱排版中积累的自定义设置，使显示更接近规范。
这一改动不仅使 alphaTab 的外观和感觉更接近其他音乐记谱软件，还允许使用自定义的 SmuFL 兼容字体。

SMuFL 字体由两个主要部分组成：

1. 字体本身，包含字形的绘制和文本布局信息
2. 一个单独的 metadata.json，包含 SMuFL 规范特定的尺寸使用细节

要激活自定义字体，需要向 alphaTab 提供这两个部分。下面的示例展示了使用不同 SMuFL 字体的同一份乐谱：

<AlphaTab tex={true}>{`
\\title "使用 Bravura"
5.3{h}.8{beam Down}
7.3{sl}.8{beam Down}
8.3{sl acc #}.8{beam Down}
7.3{h}.8{beam Down}
5.3{sl}.8{beam Down}
3.3{h acc #}.8{beam Down}
5.3{h}.8{beam Down}
3.3{acc #}.8{beam Down}
|
7.3{tr (9 16)}.1{beam Down}
|
21.1{acc #}.8{ot 8va beam Down}
21.1{acc #}.8{ot 8va beam Down}
21.1{acc #}.8{ot 8va beam Down}
21.1{acc #}.8{ot 8va beam Down}
r.2
`}</AlphaTab>

<AlphaTabPetaluma>{`
\\title "使用 Petaluma"
5.3{h}.8{beam Down}
7.3{sl}.8{beam Down}
8.3{sl acc #}.8{beam Down}
7.3{h}.8{beam Down}
5.3{sl}.8{beam Down}
3.3{h acc #}.8{beam Down}
5.3{h}.8{beam Down}
3.3{acc #}.8{beam Down}
|
7.3{tr (9 16)}.1{beam Down}
|

#### 渲染：乐谱速度可见性
https://github.com/CoderLine/alphaTab/pull/2340

这个功能是 alphaTex 整体改进的副产品。通过此改动，可以单独显示或隐藏速度变化标记。
alphaTab 现在会遵循 Guitar Pro 文件中指定的可见性信息，并且新的 alphaTex 语法允许隐藏速度标记。

如果你只在网站上显示小型乐谱片段，或者速度信息以其他方式向用户描述时，这个功能会很有用。

<AlphaTexSample player={true}>{`
// 此速度可见
\\tempo 120 
    C4 * 4 
|
// 此速度变化不可见
\\tempo (60 hide)
    C4 * 4
|
`}</AlphaTexSample>

查看相关的 [`\tempo`](/docs/alphatex/bar-metadata#tempo) 和 [`tempo` 属性](/docs/alphatex/beat-properties#tempo) 语法文档了解详情。

#### alphaTex：基于 AST 的新解析器
https://github.com/CoderLine/alphaTab/pull/2339

https://github.com/CoderLine/alphaTab/pull/2340

<img src="/img/release/v17/ast.png" />

虽然这是一个相当技术性的改动，但它是本次发布中添加的其他重要功能的基础。

一个（相当自发的）举措是改进 alphaTex 作为一门语言，使其更接近用户，允许他们在自己选择的编辑器中使用你可能开发的插件和扩展来编写 alphaTex。

为了构建新的更好的工具，提供更好的 alphaTex 编写辅助，旧的导入器（用于读取 alphaTex）不再适用。旧的导入器获取输入文本，并尝试直接将其读入 alphaTab 数据模型。
如果 alphaTex 代码中有无效内容，它会提供一些基本的错误信息。

新的解析器更接近你在 TypeScript、C# 或 Python 等编程/脚本语言中看到的内容。
借鉴编译器构造的各个方面，alphaTab 现在有了独立的词法分析器、解析器（编译器前端）和导入器（编译器后端）。

* 词法分析器和解析器将 alphaTex 代码翻译成树形结构，其中包含代码中各个元素所在位置的详细信息：抽象语法树（AST）。
对于专家来说：它接近具体语法树，因为它保留了标点和注释的信息，但不保留任何空白信息。
* 然后导入器将此 AST 翻译成 alphaTab 数据模型。
* 在任何阶段，组件都可能为文档范围报告诊断信息（警告、错误、提示）。

在这次重构过程中，我们注意到一系列潜在的改进，这些改进直接融入了新的解析器中。

alphaTex 曾经是一门相当"松散"的语言，定义了一些语言结构，但使用不一致。现在 alphaTex 更清晰地定义了如何描述元素和指定值。
详细信息现在记录在新的[语言文档](/docs/alphatex/syntax)中。

与 1.6 相比，语言的两个关键变化是：

* 文档不再需要用小圆点分隔成 3 个部分。参见[文档结构](/docs/alphatex/document-structure)。
* 元数据标签和属性现在更遵循函数调用方式，值作为参数传递给它们。单个值不需要括号，但多个值应该用括号包裹。[参见参数](/docs/alphatex/syntax#parameters--argument-lists)。

#### alphaTex：语言服务器和 Monaco 集成
https://github.com/CoderLine/alphaTab/pull/2379

为了为 alphaTex 提供最佳的用户体验，拥有某种编辑器辅助是关键。只有一个纯文本框，很难正确高效地编写 alphaTex。

##### 语言服务器

<img src="/img/release/v17/editor.png" />

多年前，微软发明了一种名为"语言服务器协议"（LSP）的协议，它定义了一种统一的方式，让（编程/脚本）语言作者可以向文本和代码编辑器（如 Visual Studio Code）提供额外的编辑器功能。

在具备了新的语言解析能力之后，创建语言服务器是下一个合乎逻辑的步骤。

https://www.npmjs.com/package/@coderline/alphatab-language-server

长话短说：此模块为兼容 LSP 的编辑器提供高级功能，包括：

1. 通过 TextMate 语法进行语法高亮，为元素提供不同的颜色，就像编写代码时一样。
2. 在编辑器中显示诊断信息，如警告和错误
3. 悬停文档，显示 alphaTex 语言元素的文档
4. 代码补全，提供上下文相关的项目
5. 元数据标签和属性可传递值的签名帮助。


在此深入了解此功能 [here](/docs/alphatex/lsp.mdx)

##### Monaco 集成

<img src="/img/release/v17/playground-editor.png" />

[Monaco](https://microsoft.github.io/monaco-editor/) 是 Visual Studio Code 中使用的代码编辑器。它提供高级编辑器功能，允许你将高级代码编辑器集成到你的 Web 应用程序中。

不幸的是，Monaco 本身没有内置的语言服务器协议支持，但它提供了自己的（非常相似的）API 来集成这些部分。

为了让你更容易在应用中将 alphaTex 语言服务器与 Monaco 一起使用，我们创建了自己的基本 LSP 集成。通过这个集成，你可以将语言服务器作为 Web Worker 启动，并将其连接到你的 Monaco 编辑器，提供丰富的编辑体验，具备你期望代码编辑器拥有的所有功能。

我们现在也在开发环境的 alphaTex 编辑器中使用此集成。

在此深入了解此功能 [here](/docs/alphatex/monaco.mdx)

#### 开发：Monorepo 设置
https://github.com/CoderLine/alphaTab/pull/2304

alphaTab 的 git 仓库被重新组织，以遵循 Web 项目中更常见的 monorepo 结构。
随着我们发布的 NPM 和其他包的增长，旧的结构不再适用。

各个模块现在嵌套在使用 NPM 工作区的 `packages` 文件夹中。
一些通用配置已被提取出来，以便在我们生产的所有包中更容易使用。

新的结构现在允许更好的代码共享，并根据各个包的需要生成各种不同的输出。

在这一点上，alphaTab 没有使用任何特殊的 monorepo 工具，如 Lerna 或 NX，而是使用我们自己的一套脚本，并尽量保持简单。我们使用 Vite 和转译器的工具链已经足够复杂了。我们不需要更多的工具和依赖项来构建 alphaTab。

#### 构建：工具链现代化
https://github.com/CoderLine/alphaTab/pull/2349

在 monorepo 重组的基础上，我们还扩展了 alphaTab 的工具和构建。其中一些也对 alphaTab 的使用者产生了影响：

##### ES2022 输出

我们决定将编译升级到 EcmaScript2022。这允许使用一些已经在所有主流浏览器中支持的新浏览器 API。

##### 命名约定检查和私有名称混淆

我们在 linter（Biome）中激活了一些命名约定检查，所有私有成员现在都以下划线 `_` 为前缀。
此外，当我们生成最小化输出 `.min.mjs` 时，我们也会混淆这些私有成员的名称。

这有利于减小代码大小，因为成员名称可以缩短。

如果你一直在使用 alphaTab 类和 API 的私有成员，你可能需要更新你的代码。如果你仍然想访问私有成员，你需要使用未混淆的版本以避免更新时的命名不匹配，并且你必须更新成员名称。

如果你在使用私有 API，我们建议提出请求，以便在未来的版本中为你的需求公开 API。

##### 快照测试

从历史上看，我们在单元测试中编写了大量手动测试断言。对于视觉回归测试，我们已经使用了快照测试，其中将黄金参考图像与新输出进行检查。

现在我们也为其他数据对象提供了此类测试支持。虽然我们在那里使用 jest-snapshot 作为基础，但实际上只有有限的断言可用。
由于我们还需要能够在 C# 和 Kotlin 中运行测试，我们不能只是传入任何特殊对象并期望它能工作。

但我们创建了各种自定义序列化器，允许更容易地针对快照引用进行测试，而不是编写手动检查。

#### alphaTex：新的生成文档
https://github.com/CoderLine/alphaTabWebsite/pull/153

随着 alphaTex 的所有变化，也需要新的文档。特别是由于 alphaTex 文档
也需要在语言服务器中提供文档悬停和代码补全，在网站上手动维护它似乎不再可行。

相反，现在大部分列出所有元数据标签、属性等的参考文档都是从 alphaTex 的中央语言定义自动生成的。

感谢这一点，当我们向代码中添加新功能时，文档将自动更新。减少了工作量，并降低了文档过时的风险。

文档现在可能看起来更技术性一些，但一旦你掌握了如何阅读和使用它，
查找信息将比以前容易得多。

[前往新的文档页面](http://localhost:3000/docs/alphatex/score-metadata)查看结果。
